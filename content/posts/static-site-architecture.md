## 一条约束，删掉了整个后端

这个站点的原始需求只有一句话：**改文章只改 Git，不碰服务器**。

把这句话拆开，其实是三个要求：内容以 Git 为唯一真相、发布过程可重复、服务器上不保留任何需要人工维护的状态。前两条指向构建期自动化，第三条直接否定了服务端会话、数据库和后台管理系统。

于是架构变成：Markdown 进仓库 → CI 构建出纯静态产物 → CDN 分发。访客拿到的每个字节都是构建时就已经确定的文件。

## 被划出去的边界

最容易被顺手做进站内的两件事，是评论和统计。它们的共同点是“需要写入”，也就天然需要服务端。处理方式是把它们整体划为**外部构件**：

- 评论交给 Giscus，数据落在 GitHub Discussions，鉴权由 GitHub 身份完成；
- 统计交给 Umami，只记匿名事件，本站不落任何个人信息。

这样划界之后，本站的领域模型里不再有 Comment 实体，也不需要“评论审核”这类用例。少了两个实体，少了鉴权、防刷、存储清理，后端就彻底不需要了。

## 内容契约比代码更重要

没有后端 API，不代表没有契约。这个站点的契约有三层：

| 层 | 载体 | 违约后果 |
| --- | --- | --- |
| 内容 | front-matter JSON Schema | 构建失败 |
| URL | `/posts/{slug}/` 等路由规则 | 死链检查拦截 |
| 外部 | Giscus 参数、Umami 事件名 | 评论或统计失效 |

第一层用 [JSON Schema](https://json-schema.org/) 在构建前校验，缺 `title`、`date`、`tags`、`slug`、`draft` 任意一项都会直接停下。这比“写个文档提醒自己”可靠得多。

## 撤回为什么是 410 而不是 404

文章生命周期里有一条不太显眼的转移：已发布 → 撤回。撤回之后旧 URL 不该回到 404，因为 404 意味着“从未存在过”，而撤回是“曾经存在、主动移除”。

这条规则不是在架构图里想出来的，是从状态图里长出来的。它最后落成了 URL 契约里的一条：撤回的文章保留路径、返回 410，并在 `_redirects` 中登记。

## 小结

零运行时的代价是构建期要做更多检查：front-matter 校验、死链检查、产物断言。收益是上线之后几乎没有运维面——没有进程要看，没有数据库要备份，也没有补丁要打。对一个个人站点来说，这笔交易是划算的。
