第一部分：需求分析。三张图加一张状态图。重点不是画图本身，而是两个边界决策。

第 1 节 · 用例图
用例图只讲两个关系：extend 表示可选扩展（评论），include 表示必然发生（统计上报）。站主和 CI 机器人共用"构建并发布"，区别只在权限。

需求 · 概念模型

五个类，一个被刻意排除

领域类

类关键属性
Postslug、title、date、summary、draft、cover
Tagname、slug（与 Post N:N）
Projectname、intro、stack、repoUrl、demoUrl
Pagetitle、body（关于、简历等固定页）
SiteConfigtitle、author、baseUrl、feedPath

边界决策

Comment 不作为本站类——由外部构件 Giscus 承担。

  • — 本站模型里不建表、不做鉴权
  • — 需求阶段就定，直接决定后续没有后端
  • — Post → Comment 只是"外部关联 Giscus"

URL 由 slug 决定：/posts/{slug}/

第 2 节 · 领域类图
领域模型五个类很常规，关键是被排除的那个：Comment。把它判给外部构件，是全文第一个决定性决策——没有评论存储，就不需要数据库，后端就此消失。

需求 · 交互与生命周期

整条时序里，没有本站服务端

顺序图 · 访客阅读一篇文章

1访客 → 静态产物：GET /posts/xxx/ → 返回 HTML
2访客 → Umami：上报 pageview（无 Cookie）
3访客 → Pagefind：输入关键词 → 匹配列表
4访客 → Giscus：加载评论 → GitHub 登录后发表

四个参与者全是静态文件或第三方——"无后端"在需求图上的直接体现。

第 3 节 · 顺序图与状态图
左：阅读时序，四个参与者没有一个是本站服务端。右：文章状态机。重点讲"撤回→410"——没有状态图，这条契约没人会想到。状态图不是装饰，它在生成需求。

第 4 节 · 逻辑视图
逻辑视图四层：内容源、构建期、托管分发、外部构件。三条约束记在图上：内容只在 Git、模板不直读内容、评论不出本站模型。这三条后面会变成 lint 规则。

架构 · 开发视图

五个包，一条红线

layouts/页面骨架components/、lib/ 纯函数

第 5 节 · 开发视图
开发视图把逻辑构件落到包结构。依赖方向单一：lib 读 content，layouts 用 lib 纯函数，components 只吃 props。红线只有一条，但足以保证"模板不直读内容"可执行、可检查。

第 6 节 · 物理视图
物理视图六个部署单元。关键链路：git push → CI → 对象存储 → CDN 回源 → 访客。访客浏览器另外直连 GitHub 和 Umami——这条直连线就是安全边界，不是偷懒，是刻意设计。

架构 · 运行视图

发布与访问：两条时序

发布流程（站主 → CDN 生效）

1git push（Markdown 变更）
2Webhook 触发 CI 构建
3front-matter 校验 · 构建 · 死链检查
4a通过 → 上传产物（指纹命名）→ 失效旧入口 → 部署成功 + 预览链接
4b失败 → 构建失败，线上产物不变

访客访问（缓存命中 / 未命中）

1访客 → CDN 边缘：GET /posts/xxx/
2a边缘命中 → 200 直接返回
2b未命中 → 回源对象存储 → 200 + 边缘缓存
≥ 95%

边缘命中率目标

第 7 节 · 运行视图
运行视图两条时序。发布侧的关键是 alt 分支：校验失败时线上产物不变——坏内容永远到不了线上。访问侧给出量化目标：边缘命中率 ≥ 95%。

架构 · 一致性核对

四张图互相对账，抓出真缺口

核对项结果
逻辑图每个构件 → 开发图有包内容→content/、构建器→lib/+scripts/、搜索→Pagefind 插件、评论/统计→外部
每个构件 → 物理图有部署单元静态产物→对象存储+CDN、评论→GitHub、统计→Umami
每条运行消息 → 有连接件Git 提交、构建调用、HTTPS、外部 API
缺口检查逻辑图有"统计"，物理图必须有 Umami，运行图必须有事件上报——第一版漏了，已补上

三张图对不上，说明架构没落地，不是画错图。

第 8 节 · 一致性核对
一致性核对是四视图的收尾。真实发生的缺口：统计构件在逻辑、物理、运行三张图里对不上。这不是画图失误，是架构没落地——核对表逼着你补上。

Part · 03

复用 · 约束 · 契约

选型会回退，约束要可检查，契约没有后端也要有三层。

第三部分：把架构变成可执行的东西。选型不是一次选对，约束不是口头约定，契约不是后端专利。

复用 · 选型表

六个可替换点，一次回退

可替换点候选选定理由
构建器Hugo / Eleventy / Astro / NextEleventy零运行时、构建秒级、输出纯静态
托管Netlify / Vercel / 对象存储+CDN静态托管免费额度、PR 预览、自带 CDN
搜索Pagefind / AlgoliaPagefind构建时生成索引，无 API key、无外部依赖
评论Giscus / DisqusGiscus无广告，数据在 GitHub Issues，符合"数据自持"
统计Google Analytics / UmamiUmami无 Cookie、轻量，符合"不采集个人信息"
图片图片 CDN / 构建时压缩构建时 sharp少一个外部依赖

一次回退

初选 Google Analytics，与"不采集个人信息"冲突 → 换 Umami。这正是活动图里「与架构约束冲突 → 换构件」那条边。

第 9 节 · 可替换点与选型
六个可替换点各自有候选与理由。重点讲回退：GA 初选后与隐私约束冲突，换成 Umami。选型表要留"回退"的位置——第一次选对是运气，能回退才是流程。

约束 · 七类检查

每条约束，都要配检查手段

类别本项目约束检查手段
分层依赖模板/组件不得直读 content/ESLint no-restricted-imports + 自定义 lint 禁 fs
单一出口所有数据经 lib/posts 获取代码审查 + grep fs.readFile
幂等同一 commit 重复构建产物一致CI 构建两次比对 hash
无状态托管无会话、无服务端状态架构评审
权限部署令牌只授单仓库；评论写权限交 GitHub 身份令牌 scope 审查
性能单页 HTML ≤ 100 KB、图片 WebP + 显式宽高Lighthouse CI 门槛
数据唯一出口内容只在 Git，产物不手改发布流程比对
第 10 节 · 架构约束检查
七类约束，每类都配了可执行的检查手段：lint 规则、CI 双构建比对 hash、Lighthouse 门槛、令牌 scope 审查。约束没有检查手段就是口号。

契约 · 三层 + 权限

没有后端 API，契约照样有三层

三层契约

层内容与载体
内容契约front-matter：title/date/tags/draft/slug/cover
JSON Schema，缺字段构建失败
URL 契约/posts/{slug}/ · /tags/{tag}/ · /feed.xml · /sitemap.xml
路由规则表 + 301 迁移表
外部契约Giscus 参数（repo/category/mapping）
Umami 事件名（pageview/share/outbound）

错误约定：404 页面、410 弃用页（来自状态图"撤回"）、RSS 必须通过 feed 校验器。

权限矩阵

主体认证方式边界
访客无只读
站主GitHub 身份可写 Git
CI 机器人部署令牌（单仓库）只构建发布
评论者GitHub OAuth只在自己权限内写评论

静态站的安全模型：能写什么，全由第三方身份决定；本站不持有任何凭证。

第 11 节 · 全局接口契约
契约三层：内容契约靠 JSON Schema 在构建期强制；URL 契约是公开承诺，改动要走 301 迁移表；外部契约封装在组件常量里。注意 410 弃用页——它来自需求阶段的状态图，前后闭环了。

目录即架构

lib/          ← 读取 · 路由 · SEO · feed
scripts/      ← 构建与检查脚本
static/       ← 静态资产

package.json  ← build / serve / lint / check

必备能力

  • — front-matter 校验（缺字段构建失败）
  • — 死链检查（lychee）
  • — Lighthouse CI 性能门槛
  • — PR 预览部署
  • — 404 页 · RSS · sitemap

完成标志

本地 npm run build 出产物，
CI 能出预览链接。

第 12 节 · 脚手架
脚手架不是随便建目录——它就是开发视图的物化：每个包对应一个目录，红线由 lint 和脚本把守。完成标志很具体：本地能构建、CI 能出预览链接。

落地 · 按用例纵切

六个切片，每片端到端可验收

S1

S6

S1 四项端到端检查：验收脚本可执行 · 无 mock 与 TODO · 产物文件真实存在 · 坏路径 /nope 返回 404

第 13 节 · 切片
切片按用例纵切，不按层横切。每片都有可执行的验收脚本——"当访问 / 时应看到 3 篇文章"这种句式。S5 的验收甚至跨到 GitHub：发一条评论，看 discussion 是否出现。

第 14 节 · 详细设计
S1 详细设计只有五行。这不是偷懒：内容模型来自领域图，异常路径来自状态图，约束落地来自七类检查——前面的工作做薄但做全，详细设计自然只剩一张表。

结论 · 五条

走完十四个环节，记住五句话

  • ① 小项目不用减步骤，只需每步更薄

    十四个环节一个没省，但每步只有一两张表、一两张图。

  • ② 需求阶段的两个决策决定了整个架构

    评论判为外部构件、内容以 Git 为唯一真相——这两条一定，后端就不需要了。

  • ③ 状态图生成了契约

    "撤回 → 410"不是从架构图来的，是从状态图来的。

  • ④ 一致性核对抓出了真缺口

    统计构件三张图对不上，说明架构没落地，不是画错图。

  • ⑤ 复用会回退

    GA 换成 Umami，正好演示了活动图里"换构件"那条边。

第五部分 · 走查结论
五条结论，每条都对应走查中的一个真实瞬间。核心信息：方法论不分项目大小，分的是每一步的厚度；而图与图之间的对账，比任何一张图本身都值钱。
